## Как запускать

1. Передайте Grok-боту весь файл и промпт A. Приложите ссылку на репозиторий, если бот ещё не знает, где находится код сайта.
2. Передайте Cursor этот же файл и промпт B. После проверки первого этапа передайте C, затем D. Каждый этап рассчитан на отдельный набор изменений с проверяемым результатом.
3. На первом этапе на тестовом сайте должны работать каталог, пункт меню, два режима расчёта регистрации, калькулятор продления и редактор МКТУ. Следующие этапы опираются на общую логику и интерфейс из B.

## Общие требования для Cursor

В каждом из промптов B, C и D слова «задание» означают этот файл целиком.

- Работай внутри текущего репозитория. Переиспользуй шаблоны, стили, меню, кнопки, аналитику, генерацию sitemap и существующую форму «Лирейт». Примени правила репозитория и его команды сборки. Веди отдельную ветку или изолированную рабочую копию на этап.
- Добавь пункт «Патентные задачи» в главное меню, включая мобильную версию. Для каталога используй H1 «Патентные задачи» и четыре блока «Подготовка заявки», «Свидетельство и реестр», «Платежи», «Помощь с ФИПС». Сначала показывай инструмент, а затем справку, пример и следующий шаг. В меню и sitemap включай готовые страницы. Пустые группы скрывай до появления инструментов.
- Исходная точка дизайна — интерфейс «Лирейт». Для каждой страницы предусмотрены понятные подписи к полям, «Пример», «Очистить», результат рядом с формой и копирование только соответствующего результата там, где оно нужно. На мобильном удобны крупные элементы управления, доступные с клавиатуры переключатели, читаемая разбивка суммы и отсутствие горизонтальной прокрутки.
- Для готовых публичных страниц задай собственные title, description, H1, канонический URL и хлебные крошки по стандартам сайта. Используй ссылки со страниц `/mktu`, `/registraciya_tovarnogo_znaka/`, `/prodlenie_tovarnogo_znaka/`, `/findtz/`, `/kak-zaregistrirovat-tovarnyy-znak-samostoyatelno-2026/`, `/registraciya_programm_evm/` там, где они помогают продолжить задачу. Перед изменениями проверь ответ, канонический адрес и фактический шаблон каждой страницы.
- Под результатом по смыслу добавь один переход к существующей услуге. Для регистрации, продления и изменений используй текущую форму или страницу услуги. Если у формы уже есть интеграция с amoCRM, передавай только идентификатор инструмента и страницу источника. Сам расчёт и исходные данные уходят только по явно выбранному пользователем сценарию с понятным составом передаваемых сведений.
- Для Метрики используй существующий счётчик, если он есть. События — открытие инструмента, успешный расчёт, скачивание и переход к консультации. В параметрах только идентификатор инструмента, режим и статус. Исключи содержимое полей, буфер обмена и платёжные данные из аналитики и журналов. Проверь фактическую маскировку форм в записи сессий.
- Локальные операции выполняй в браузере, когда это позволяет текущий стек. Передавай расчёт между инструментами внутри интерфейса. При раздельных страницах разрешены только обезличенные числа и тарифные пункты во временном состоянии с удалением после передачи. Сырые перечни, названия знаков, адреса и платёжные поля оставляй в памяти текущей страницы. На связанной странице допустимы ручное копирование и повторный ввод. Для запросов к официальным системам показывай внешний адрес и отправляй поля только после явного действия пользователя.
- Пошлины, правила и справочные данные держи в версионируемых наборах. Для правила запиши идентификатор, дату вступления в силу, дату проверки, нормативный пункт и URL источника. Для отдельных спорных случаев фиксируй основание и возвращай справочный результат с понятной причиной, почему точная сумма требует уточнения. Если официальные страницы расходятся, приложи расхождение в отчёт по этапу.
- Сервисы VAU используй для изучения сценариев. Реализацию, интерфейс, тексты и тестовые примеры создай для «Лирейт». Формулы, реквизиты, контакты и требования к файлам сверяй с первичными источниками. Для самой реализации используй общие смежные компоненты сайта и одну версию формул.

## Промпт C — этап 2. Адрес, файл знака, изменения и контакты

```text
Продолжи раздел «Патентные задачи» по приложенному заданию. Переиспользуй каталог и расчёт из этапа 1. Сделай пять страниц. Для каждой страницы проверь прямой переход, мобильный сценарий и основной пользовательский результат.

1. Адрес заявителя. Пользователь вставляет адрес, видит исходник и предложенный вариант для заявки. Обработай пробелы, регистр и допустимые сокращения по проверенным правилам. Сохраняй индекс, корпус, строение, литеру, помещение и другие значимые элементы. Адрес заявителя и адрес для переписки — разные поля и сценарии. Дай ручную правку и копирование. Внешнюю сверку ГАР/ФИАС подключай только через поддерживаемый источник. При неточном совпадении покажи варианты, при недоступности источника — локально отформатированный результат с отметкой «Адрес не проверен по ГАР». Для иностранных или неполных адресов предлагай ручную проверку. API-ключи храни на сервере.
2. Файл словесного знака. Форма принимает текст с кириллицей, латиницей и знаками препинания, показывает предпросмотр и скачивает TIFF. По требованиям выбранного канала подачи проверь размеры, 300 dpi, RGB 24 бит, ограничения по формату и сжатию. Если используется квадрат максимального размера 8 × 8 см, 944 × 944 пикселя при 300 dpi укладывается в предел. Для светлого непрозрачного фона обеспечь одинаковую раскладку в предпросмотре и скачанном файле. Подключай гарнитуры с подтверждёнными правами на распространение и рендеринг. Проверь фактический TIFF независимым декодером, включая метаданные, масштаб, обрезку длинного текста, переносы и отсутствующие символы. Для загрузки на рабочем месте проверь файл на тестовых данных в поддерживаемом канале, если есть доступ, без отправки заявки.
3. Изменения в свидетельстве и реестре. Дай выбрать виды изменений и количество регистраций. Покажи отдельные строки по 2.16 и 2.17, возможный бумажный документ, основание и применимость для каждого вида. По 2.16 разбей расчёт за каждое изменение по каждому знаку. Отдельно обрабатывай ошибки заявителя, ошибки ведомства, изменения сведений о правообладателе и сокращение перечня. Для применения 2.17 спрашивай, есть ли соответствующие сведения в выданном свидетельстве, и уточняй дату выпуска только при подтверждённом правиле. Приведи сценарии, где ставка зависит от фактического содержания документа. При сомнении оставь конкретную строку «Требуется уточнение» и покажи рассчитанные позиции. Приведи ссылку на официальное заявление.
4. Сокращение перечня МКТУ. Пользователь вставляет исходный блок (511), проверяет разбор и отмечает позиции, которые остаются. Обе выдачи, сохраняемые и исключаемые позиции, должны содержать исходные формулировки и классы. Привязывай выбор к позиции исходника, чтобы одинаковый текст в разных классах оставался различимым. Запрашивай отдельное подтверждение при исключении целого класса. При удалении всех классов объясняй, что расчёт продления недоступен. Показывай пошлину за продление до и после и стоимость изменений отдельными строками. Для расчёта разницы учитывай подтверждённые количества и отдельно показывай чистую разницу после расходов на изменение, если известны все суммы. Для старых списков используй предварительный просмотр разбора и ручное подтверждение границ.
5. Контакты ФИПС и Роспатента. Дай поиск по ведомству, подразделению, теме и названию услуги. Для контакта покажи тип обращения, кликабельный номер или e-mail, официальный источник и дату сверки. Бери актуальные публичные служебные контакты. Для пустой выдачи покажи ссылку на официальный справочник.
6. Проверь неоднозначный адрес, длинный словесный знак, две регистрации с несколькими изменениями, исключение целого класса, совпадающий термин из двух классов, сохранность исходных запятых и пустую выдачу контактов. Приложи источники, проверенные URL и сведения о том, что требует ручной сверки.
```

## Промпт D — этап 3. Платежи и АРМ «Регистратор»

```text
Реализуй этап 3 из приложенного задания. Начни с матрицы источников, подтверждённых реквизитов, доступных методов, авторизации и допустимых данных для каждого внешнего сценария. Для недоступной части подготовь понятную страницу с официальным переходом. Подключай реальный поиск и платёжный QR после проверки текущего контракта и реквизитов в тестовом контуре.

1. Генератор оплаты патентных пошлин Роспатента. Принимай выбранные тарифные пункты, подтверждённую пользователем сумму и необходимые по официальной форме сведения для конкретного этапа. Из калькулятора передавай только выбранные к оплате строки и сумму. Сначала показывай получателя, счета с понятными наименованиями, КБК, назначение, сумму и ссылку на реквизиты. Дай скачать QR и распечатать образец с реквизитами. Образец обозначь как черновик, который пользователь сверяет и использует в своём банке. Фиксируй версию, дату проверки и источник профиля. Если профиль не подтверждён, покажи официальную страницу реквизитов без генерации платёжного QR.
2. Генератор оплаты платных услуг ФИПС. Отдельный режим, отдельный профиль реквизитов и отдельное назначение. Проверь официальный перечень и правила заполнения. Сумму указывай по счёту или проверенному тарифу. Различай платную услугу, патентную пошлину и государственную пошлину за ПрЭВМ. В текущем задании две страницы QR — для патентной пошлины и для платной услуги ФИПС. Для пошлины за регистрацию ПрЭВМ оставь ссылку на официальные правила оплаты. Проверяй соответствие QR действующему формату по документации, декодируй фактическое содержимое независимым декодером, сверяй каждое поле с видимой платёжной формой. Проверь распознавание в поддерживаемых банковских приложениях без исполнения платежа. Протестируй неправильную сумму, смену профиля, неполные и устаревшие реквизиты.
3. Поиск платежа по ПрЭВМ. Одна страница, два режима. Для организации ожидаемые поля — номер и дата платёжного документа, ИНН, КПП. Для физлица — номер, дата и ФИО. Подтверди фактический контракт, поддерживаемый метод и допустимость передачи этих полей на стороне официального сервиса. При доступном интеграционном маршруте различай «Платёж найден», «Платёж не найден», «Сервис временно недоступен» и «Требуется вход». При отсутствии подтверждённого маршрута дай ссылку на личный кабинет или официальный канал сверки и перечень данных, которые пригодятся пользователю. В этом состоянии оставь только справочные поля или пример. Историю поиска не сохраняй. Проверь, что платёжные и персональные данные не уходят в параметры аналитики и внутренние URL сайта.
4. Старые заявки. Проверь официальное руководство и доступный способ открыть собственную старую заявку в АРМ «Регистратор». При подтверждённом маршруте пользователь вводит номер и переходит в официальный личный кабинет под своей учётной записью. При отсутствии документированного перехода открой официальный АРМ и покажи инструкцию поиска или обращения в поддержку. Полномочия и авторизацию проверяет официальный сервис. Публичная страница «Лирейт» не принимает учётные данные ФИПС. Проверь отдельные случаи: действующий доступ, запрос авторизации, отсутствие права, неизвестный номер. Если в проекте уже есть связка amoCRM → АРМ, используй её только в подтверждённом внутреннем контуре и по действующему контракту.
5. Проверь сквозной сценарий «редактор МКТУ → калькулятор → выбор этапа оплаты → проверка реквизитов → QR или официальный переход». Для каждого внешнего сценария приложи ссылку на официальный источник, результат тестов, поддерживаемые статусы и условия отключения. Публикуй рабочий публичный сценарий и явно обозначай внешний переход там, где действие выполняется в сервисе ведомства.
```
